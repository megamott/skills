# Код-ревью по правилам проекта

Проверяй выбранные изменения; остальной код читай для понимания их последствий. Не меняй код, не создавай коммиты и не публикуй комментарии в PR без поручения пользователя.

## Определи область ревью

- Используй указанные пользователем файлы, коммит, диапазон или PR. Для коммита смотри только его изменения, для диапазона — заданные границы. Ветку сравнивай с базой через `git diff <base>...HEAD`, без незапрошенных локальных изменений.
- Без явной области проверь `git status --short`. Ревьюй staged и unstaged через `git diff HEAD`, а новые файлы из `git ls-files --others --exclude-standard` читай отдельно. До первого коммита читай все добавленные и новые файлы.
- Если локальных изменений нет, используй базовую ветку из запроса; если она неизвестна, уточни область. Не выбирай произвольный последний коммит.
- Для сравнения истории зафиксируй границы в SHA через `git rev-parse` и используй их в diff. Для ветки прочитай `git log <base-sha>..<head-sha> --oneline`. О неверной ссылке или пустом diff сообщи; другую базу не подставляй.

Перед анализом кратко назови выбранную область.

## Собери правила и требования

- Прочитай применимые `AGENTS.md`, `CLAUDE.md`, `CLAUDE.local.md` в родительских и затронутых каталогах. Документ и его симлинк достаточно прочитать один раз.
- Изучи относящиеся к изменениям разделы `CONTRIBUTING.md`, `CODING_STANDARDS.md`, архитектурных документов и указанных проектом скиллов, если они доступны. Обязательных зависимостей от других скиллов нет.
- Следуй запросу пользователя и действующим инструкциям агента. Вложенные правила действуют в своих каталогах; проектные исключения важнее общих рекомендаций. Не выдавай личные предпочтения, правила других проектов или отдельные примеры соседнего кода за требования.
- Возьми спецификацию из запроса или явно связанного локального документа. Если её нет, не требуй её и не ищи в трекере. Продолжай по доступным данным; отсутствие требований и недоступные источники отметь в отчёте.

## Проверь изменения

Читай diff, окружающий код, вызовы и тесты. Проверяй:

- **Поведение:** ошибки, регрессии и уязвимости. Подтверждай их кодом и контрактами, а не неизвестными предпосылками.
- **Требования:** пропуски, частичную или неверную реализацию, необоснованный выход за задачу. Необходимые вспомогательные изменения допустимы. Соблюдение стиля не доказывает выполнение задачи.
- **Правила проекта:** архитектуру, стиль и тесты. Не навязывай стек, уровень тестов или каталог code smells. Недостающий тест связывай с конкретным риском или требованием.
- **Нейминг:** имена должны передавать назначение, а у функций — действие и существенные побочные эффекты. Предлагай точные имена в терминах проекта вместо общих слов и неясных сокращений. Для списания оплаты `charge_invoice` точнее, чем `get_total`.
- **Дублирование:** ищи повторы логики, которую нужно менять согласованно, и предлагай простое общее решение. Не объединяй код с разными причинами изменения и не добавляй абстракции ради DRY.
- **Простоту:** предлагай понятные упрощения без изменения поведения. Ищи лишние условия, вложенность, преобразования, обёртки и расширения «на будущее» без потребителей. Например, булево значение можно вернуть без ветвления. Сохраняй нужные архитектурные границы; меньше строк не всегда значит проще.

При необходимости запускай локальные проверки без автоисправлений. Пропускай замечания о форматировании, уже покрытом настроенным линтером или форматтером; сбои проверок сообщи в отчёте.

## Выдай результат

Пиши на языке пользователя и соблюдай заданный пользователем или проектом формат. По умолчанию начни с замечаний по важности. Для каждого укажи:

- важность, тип (ошибка, нарушение правила или требования, рекомендация) и суть;
- файл, минимальный участок изменённых строк, условия и последствия;
- основание: конкретный пункт правила или спецификации, доказательство ошибки либо трудность чтения и сопровождения;
- направление исправления; короткий пример — если он помогает.

Включай только обоснованные замечания по выбранным изменениям. Старые проблемы вне области ревью, повторы, вкусовые придирки, похвала и пустые категории не нужны. Если замечаний нет, скажи прямо. Заверши результатами проверок и ограничениями: что недоступно или не проверено. Не требуй перехода к исправлениям.
